ホームの外枠や静的セクションは段階3以降に作れるが、全欄の完成判定は連携と各ページが揃う段階7で行う。

## 0. 対象と比較基準を確定する

- [確定事項](decisions.md) とページ台帳を確認する。質問した6項目は回答済み。
- 旧サイトの採用 URL、主要な状態、ナビと外部リンクを一覧化する。ブログを回収しないことと、ページを廃止することを混同しない。
- 公開サイトを同じブラウザ・フォント・幅で撮影し、比較基準を保存する。390 / 768 / 1440px と450 / 600 / 1000pxの境界前後を確認する。
- メニュー開閉、スクロール、カルーセル、動画、カード、記事本文の状態を記録する。
- Cloudflare Pages の既存プロジェクト・公開設定を調査し、Vite の配信形式・深い URL・初期 HTML の OGP の実現方法を決める。ドメインは `compositecomputer.club` を継続する。

**完了条件:** 採用・削除対象、旧 URL とUI基準が明確。公開先は Cloudflare Pages とし、実設定の調査を公開直前まで持ち越さない。確認待ちの連携があっても、依存しない雛形・静的コンテンツの実装は進められる。

## 1. 開発基盤を用意する

- Toybox から package / lockfile、Node・npm、TS、Vite、Biome、命名チェックを移植する。scripts の参照先も揃える。
- `main.tsx`、ルートを定義する `App.tsx`、`pages/`・`features/`・`shared/`・`util/` の構成を作る。
- CSS Modules、alias、strict TS、命名規則を有効にする。
- Storybook の表示・必要な操作テスト、Husky / lint-staged、GitHub Actions を [開発環境と CI](development-and-ci.md) に沿って用意する。
- 最初の状態で dev / build とクリーンな `npm ci` が動くことを確認する。CI workflow の実行確認は、GitHub 側で実行できる段階で別途記録する。

**完了条件:** package と lockfile が一致し、`npm run ci` が成功。Storybook が起動でき、参照切れがない。アプリと異なる Toybox 固有の画面を混入させない。

## 2. ローカル content と Markdown を整備する

- [コンテンツ構成](content-structure.md) に沿って、本文・表示設定・画像・動画を同じページ・記事フォルダへまとめた `content/` を作る。回収原本のID付きファイルを日常の編集先にしない。
- `NewsEntry`、`CommunityEntry`、`Author`、`Tag` 等の型を定義し、`contentRepository.ts` で読込と参照解決を行う。
- 原本から紹介・5分野・全お知らせを変換し、著者はContentful取得に分離する。旧 ID、本文、日時、重要フラグ、タグ・著者参照を保持する。
- 回収 URL とローカルメディアの対応表を使って、本文・サムネイル・動画・poster・アイコンを置き換える。404のDiscord画像参照は運用本文から削除し、原本を保持する。
- `content/featured-works/<slug>/` に掲載作品情報と `assets/` を用意する。初期の選定・順序は現行作品欄を比較元にして確認する。
- Toybox の MarkdownPreview と依存部品を移植し、CSS を部品ごとに配置する。
- ID重複、参照先の欠落、ローカルファイルの不存在を検出する content 検査を用意し、build 前の検査へ組み込む。大量の原本 JSON 自体をアプリとして配信しない。

**完了条件:** ローカル管理の本文・メディアを外部Contentfulへの通信なしでプレビューできる。参照変換に欠落がなく、記事内の相対画像が解決される。ニュースのテンプレートから記事フォルダを追加するだけで検出され、下書きの本文・画像が公開成果物に混入しない。

## 3. 共通レイアウトを実装する

- `features/AppLayout/` に Header・Outlet・Footer を配置する。
- Header / Footer、ロゴ、ナビ、メニュー、背景マスク、スクロール動作、パンくず、必要な Button / Card 等を実装する。
- お問い合わせのフォーム・完了画面は作らず、Header / Footer の導線と sitemap から除く。旧URLは404として配信段階でも確認する。
- フォント・ライト / ダークの共通トークンを定義し、部品の見た目は各 `index.module.css` に置く。
- Toyboxのテーマ管理と切替ボタンを移植し、PC・モバイルのJP / EN位置へ配置する。保存済みテーマ・OS初期値・ページ間の同期を確認する。
- キーボード・focus・モバイル表示と、現行サイトの配置・寸法・動作を確認する。

**完了条件:** 各ページで共通部分を再利用でき、スタイルが他ページへ漏れない。既存のメニュー・外部リンク・無効項目の扱いが決定内容と一致する。

## 4. About と5分野を実装する

- `AboutPage`、`CommunityPage` と対応 feature を実装する。
- 紹介本文、概要、ロゴ、5分野へのリンクを配置する。
- 各分野の Markdown と動画を表示し、autoplay・muted・loop・poster・比率・モバイル再生を確認する。
- 分野を `/community/game`・`/community/3dcg`・`/community/hack`・`/community/2dcg`・`/community/music` で表示する。旧IDのURLから転送しない。旧ID・未知slugは404とする。

**完了条件:** Aboutは既存URL、5分野はslugの新URLで開き、本文・画像・動画がローカル管理に移行している。作品欄はホームと共用の静的掲載データで表示し、実行時に作品APIを呼ばない。

## 5. お知らせと著者を実装する

- 一覧・詳細、カード、日付、タグ、重要なお知らせ、サイドバー等の採用要素を実装する。
- 回収した16件を対象に、旧 ID の詳細 URL が開くことと一覧順を確認する。テンプレートから新規ニュースを追加し、コード・手動の一覧配列を変更せずに公開状態と日時に応じて一覧・詳細へ反映されることを確認する。
- Contentful APIから取得する公開プロフィール36名すべての著者ページと旧URL・著者リンクを実装する。ローカルプロフィールは使わない。著者別ブログ一覧の表示領域を用意し、Contentfulへの接続は段階6で完成させる。
- 通常・長文・画像あり・動画等の代表記事で、旧表示と新 Markdown の差を確認する。

**完了条件:** お知らせ本文、サムネイル、タグ・著者への参照が欠けない。未存在の ID、絞込み、直リンク・再読込・見出しアンカーを確認できる。

## 6. 外部連携を実装する

- Contentful＋Toyboxのブログ一覧・詳細と、Contentfulの著者別ブログ一覧を接続する。混在する取得元と ID を区別する。
- ブログ本文は Toybox の MarkdownPreview で表示し、画像・コード・HTML等の実文書を確認する。本文のローカル全量回収は行わない。
- 外部 API の空・失敗・再試行を確認する。ブログAPIの停止でローカル紹介・お知らせ・掲載作品を表示できなくしない。

**完了条件:** 採用した連携が実際の接続先で動き、CORS・リンク・失敗表示を確認済み。現在のToybox直接CORSはユーザー指定で後続に保留し、この条件はまだ満たしていない。プロキシは追加しない。
未採用機能はページ台帳とナビに反映する。旧分野IDのURLと削除するお問い合わせは転送せず404として扱う。

## 7. ホームを完成させる

- タイトル、ニュース切替、重要記事カルーセル、C3紹介、5分野、作品、ブログを採用仕様どおりに組み立てる。
- 個別ページと同じデータ・カード・Markdown 部品を再利用する。
- 欄の順序、余白、スクロール、切替時刻、hover・touch 操作を確認する。

**完了条件:** 外部連携を含めたホーム全体が揃い、PC / モバイルで現行 UI と比較できる。仮データやダミーの成功状態が残っていない。

## 8. 全体検証と公開候補を作成する

- `npm run ci`、content 検査、影響範囲の Storybook・ブラウザ確認を実施する。
- 採用する全ルート、分野の新slug URL、維持する既存URL、タグquery、アンカー、戻る・進む、直リンク・再読込を確認する。旧分野IDのURLは転送されず404になることを確認する。
- PC / モバイルのライトで旧サイトとUI比較し、各段階で残った差を解消する。ダークは追加仕様として全ページの配色・操作・Markdownを確認する。
- ブログ API を利用できない状況でもローカル本文・掲載作品・メディアを確認する。
- sitemap / robots、canonical、ページごとの title / description、初期 HTML の OGP を用意する。JS実行後だけの metadata 更新で OGP 対応済みにしない。
- Cloudflare Pages で深い URL、正しい asset path、HTTPS、cache、404 status が成立する配信設定を作る。削除対象の `/contact` / `/contact/thanks` も確認する。
- 最終データ反映と公開後確認、旧版へ戻す手順を具体化する。

**完了条件:** 公開前に必要な検証が揃い、残課題ごとに解消済み・採用しない・承認待ち等を区別して記録できる。未動作の採用機能を残したまま完成にしない。

## 9. 公開環境で検証して切り替える

1. 現行配信設定・旧成果物を保持し、復旧する対象と手順を確認する。
2. Cloudflare Pages の確認環境で公開候補を配信し、実際のブログ API / CORS / 動画 / OGP / 直リンクを確認する。
3. 初回回収後の更新差分を再取得し、新しい snapshot として比較する。記事・画像の追加、更新、削除とブログ側の変更を確認する。
4. 最終データで build・必要な検証を行い、公開する成果物とソースの版を対応付ける。変更点と確認結果を公開前にレビュー可能な状態にする。
5. 公開切替の許可範囲を確認したうえで、現行ドメインの配信を新版へ切り替える。キャッシュ更新は必要な範囲に限定する。
6. 現行ドメインでホーム・About・5分野・お知らせ・ブログ・著者を確認する。画像、動画、ブログAPI、静的掲載作品、削除ページの404を再確認する。

**完了条件:** 本番の採用URL（分野はslug形式）で表示・動作を確認し、重大な欠落・配信エラーがない。問題があれば、旧成果物・配信設定へ戻して確認する。
決定していないURL変更・画面欠落、ローカル本文の表示不能、主要メディア・採用連携の停止等は、切替継続か復旧かを判断する対象とする。

## 10. 切替後の監視と引継ぎ

- 運用担当と合意した観察期間中、配信エラー・404・メディア・外部連携を確認する。
- お知らせ・分野・画像を実際に追加できる更新手順、build・公開・復旧手順、連携先設定を文書に残す。
- 最終の確認結果と既知の欠損・判断をまとめ、各ガイドの「未導入」「予定」を実装状態へ更新する。
- 旧 frontend は復旧期間が終わるまで保持する。backend や Contentful は他サービス・ブログが利用する可能性があるため、このリプレイスだけを理由に停止しない。

**リプレイス完了:** 採用したページが本番で動作し、UI・URL・コード構成・CSS分割・ローカル文書管理の要件を満たし、運用担当が継続更新と復旧を行える状態。
旧サービス・原本の削除は、この完了判定とは分けて扱う。
